Fixture bug diagnosis (found and fixed this pass, in test code only):

The PR 924 fixture's original pass-4 design (before this pass's fix) blocked on a plain
`read -u 3 -r _` (no `-t`) against a writer-less private FIFO while waiting for TERM, transitioning
to a timed `read -t 1` poll loop only after the MAIN LOOP body next executed and observed a state
flag set by the trap. Isolated repro scripts (all under
`/tmp/pro-gate-pass4-114-20260901-0029/`, disposable scratch) established, empirically:

  repro-diag.sh / repro-diag2.sh: a SINGLE external `kill -TERM -- -$producer` call against the
  `timeout --signal=TERM --kill-after=30`-wrapped child reliably produces TWO `TERM_RECEIVED`
  trap-handler invocations, sub-millisecond apart, every trial. This is `timeout`'s own signal-relay
  behavior, not a bug in the fixture or in run_oracle.

  repro-diag2.sh (single-TERM, 5-second observation window): after those two back-to-back trap
  invocations complete, a plain blocking `read` that was interrupted NEVER resumed for the full
  5-second observation window (a diagnostic `LOOP_TOP_N` event, emitted at the top of every loop
  iteration, stopped incrementing after `LOOP_TOP_1` and never reached `LOOP_TOP_2`). This
  reproduced even with the single external kill call, i.e. it is the DOUBLE delivery from ONE
  TERM, not a second explicit signal, that triggers the wedge.

  repro-diag3.sh (same setup, but the loop ALWAYS uses `read -t 1 -u 3 -r _` instead of a plain
  blocking read, before AND after TERM is seen): `LOOP_TOP_N` and `DRAIN_TICK_rcN` events continued
  incrementing every ~1.003 seconds for the full 5-second window, cleanly. This isolated the fix:
  never issue an untimed blocking `read` in this fixture; always use a re-armed 1-second timed read.

  repro-fixture.sh (12 iterations, using the exact current heredoc body of the real
  `tests/engine.test.sh` PR 924 fixture, driven through the REAL `bin/oracle-review.sh` engine
  against the real `mock-cdp.mjs` server, not a simulation): 12/12 iterations show
  `READY, TERM_RECEIVED(+), RESISTING_AFTER_TERM, DRAIN_TICK x3` in the required order, `rc=6`
  every time. `pgrep -g <fixture-captured pgid>` was checked directly for iterations 10, 11, and 12
  and returned empty (exit 1, no matches) in all three, confirming no surviving descendant.

The fix applied to `tests/engine.test.sh`'s real PR 924 fixture (lines ~1428-1461):
  1. `RESISTING_AFTER_TERM` is now recorded synchronously inside `on_term()`, one-shot guarded by a
     `resisting` flag, rather than from the main loop noticing a `term_seen` state transition.
  2. The main loop unconditionally does `read -t 1 -u 3 -r _ || true` on every iteration (both
     before and after TERM), and emits `DRAIN_TICK` only once `term_seen -ge 1`. There is no longer
     any code path that issues a plain untimed blocking `read`.
This is a test-fixture-only change. No production file's trap grace, `--kill-after`, signal target,
wait/reap sequence, or proof-revocation logic was touched by this diagnosis or fix.
