Grounding Context

Codebase Context

  • Caller protocol (skills/pro-gate/SKILL.md): precheck → ~7 guardrail steps → detached launch with no caller timeout → poll <out>.status every 1–2 min for up to 47+ min p90 → branch on 13 exit codes → on exit 9, wait and re-invoke --harvest → §6 re-review loop with caller-held convergence bookkeeping, repeatable up to 8× per PR. No blocking mode, no callback, no push/notify/wake mechanism anywhere; the polled status file is the only signal surface. The wait ceremony is maintained in three places (SKILL.md, agents/oracle-reviewer.md, a hand-rolled sleep 60 loop in daemon/daemon.sh's prompt string).
  • Slot lifecycle: two stacked lock layers (per-change + account slot), each polling 3s up to 40 min. Reservations carry a generating|complete state since v0.33.0 (PRs #82/#83): a finished review no longer occupies capacity, and pg_report_capacity_holders names each holder plus the exact free-it command — but only on throttled stderr, never in the polled status file.
  • Round governor (v0.31): base 3 rounds, +1 per strictly-shrinking re-review, immovable ceiling 8, 2-strike churn brake. Trajectory state is computed every round and surfaced only at refusal (exit 12) or via pull-only --status. No cost accounting of any kind exists in the repo.
  • Institutional constraint (docs/solutions/…/ship-the-legible-core-let-the-gate-decline-fragile-automation.md): prefer a clear message over a clever mechanism, especially near credentials/quota/environment; fragile automation historically got repeated FIX-FIRST findings from the gate itself and was dropped.

Usage Forensics (Aug 3–17: 579 runs, vs prior 14d: 272)

  • Exit-7 lock-timeouts went 0 → 31, all Aug 14–16; callers slept the full configured wait (23×2400s, up to 7200s). Seven logs blame capacity held by uncollected finished reviews; v0.33.0 (installed Aug 15) fixed that class mid-window, but timeouts continued into Aug 16.
  • Exit-9 (deferred harvest) grew from 3.3% to 19.5% of all runs; clean share fell 76.8% → 64.1%; clean p50/p90 durations rose 14–19%.
  • Caller-side ceremony, PR #1628 transcript: 65 background-poller invocations, 9 re-arm recoveries, 8 poller failures (exit code 3), 4 “queued behind another session's slot” messages; session ended at ~100% context / ~$443.
  • Verdicts in window: 32 FIX-FIRST vs 4 SHIP; exit-12 round-cap hits concentrating (6 of 8 all-time in Aug 4–16); 9 reservation-TTL expiry orphans, oldest ~13h.

External Context

Independent sources converge on one architecture for agents waiting on long external jobs: start/poll split with a durable handle, the wait as a suspended first-class state, and wake-not-poll — polling surviving only as a named degraded fallback (AWS Durable Execution, Cloudflare Agents, production postmortems). Supporting numbers: virtual-queue UX research puts 20–160 min waits entirely in “walk away and get pushed the result” territory; SLURM ships estimated start times and usage-decayed fair-share; the 2026 AI-review market pairs a fast shallow reviewer with a slow deep one rather than gating everything on the expensive model; push channels in production (Kubernetes watch) still keep a poll safety net.

1. The wait leaves the session: a blocking --wait verb + wake-on-terminal

caller-wait-protocol Confidence 90% Complexity Low
Description
Give the engine a blocking verb — oracle-review.sh --wait <out|marker> [--timeout S] — a zero-token shell process that sleeps in a loop until <out>.status goes terminal, then prints the final status JSON and exits, with distinct exit codes for “review reached a verdict” vs “I lost the ability to observe” (the poller-escalation rule, folded in). The documented protocol becomes: launch, record the marker, run --wait with run_in_background, end the turn — the harness's own background-completion notification is the wake; no per-poll LLM turns exist anywhere. Cross-session and dead-session delivery stays pull-based on the durable pieces that already exist (completed store, PR comment, --status) — the production lesson from push channels is to keep exactly that safety net. The headless daemon benefits too: it blocks on --wait instead of a sleep 60 prompt loop, sidestepping its no-notifications constraint entirely.
Axis
caller-wait-protocol
Basis
direct: PR #1628 transcript: 65 poller invocations, 9 “Re-arm corrected poller” recoveries, 8 poller failures with exit code 3, session ended at ~100% context / ~$443. daemon/daemon.sh:234 hand-rolls the same loop inside an LLM prompt (“sleep 60; cat the status file”). Verified: no notify path exists anywhere in bin/lib/daemon/SKILL.md. external: wake-not-poll production pattern (Aura; AWS waitForCondition suspends at no compute cost); NN/g queue research: past ~20–30 min, people must walk away and be pushed the result.
Rationale
This is the idea most directly traceable to the incident: the hand-rolled r3-poller.sh in a job tmp dir was a per-session, per-caller reimplementation of exactly this missing verb, and it crashed 8 times. A blocking CLI verb is the smallest true fix — a ~60-line legible loop in the engine rather than a notification bus — and it doesn't deduplicate the poll ceremony across the three prose copies, it deletes it: SKILL.md §3 collapses to “run --wait in background.” Deleting protocol beats synchronizing it. This is also stage 1 of a two-stage stack: idea 5's round-loop supervisor consumes this primitive; built without it, the supervisor would just move poller fragility down one level (an LLM subagent polling for 47 minutes).
Downsides
The --wait process is tied to the session's shell lifetime — if the session dies, only the wait dies; the run, status file, and marker survive and recovery is unchanged (a good failure mode, but callers must know re-arming is free). --timeout must exceed the worst-case lock+generation envelope or exit through the distinct lost-observability code, never a false “review failed.”

2. Status v2: one additive schema change at the status choke point

queue-observability Confidence 90% Complexity Medium
Description
Enrich the JSON that pg_status() already writes on every phase transition with the state the engine already computes and then discards or hides: holders[] (which markers hold capacity, generating vs complete — awaiting collection, with the free-it command), an elapsed-in-phase heartbeat (fresh ts re-writes so silence stops being the only signal that Pro is thinking), next_action {cmd, terminal, wait_class} replacing the 23-line exit-code prose branch, a stable recover_reason_code enum for the five free-text recovery reasons, a TTL countdown on completed-but-uncollected reservations, and the round governor's rounds_used / rounds_granted / streak so exit 12 becomes an anticipated checkpoint instead of a surprise. Sequencing: two fields ship inside idea 1's stage-1 PR — a literal terminal flag + next_action (they are --wait's loop condition and wake payload) and the heartbeat (it defines the staleness that makes the lost-observability exit reliable). The rest is additive and can trail a release; the rounds preview and reason enum ideally land before or with the stage-2 supervisor, their real consumer.
Axis
queue-observability
Basis
direct: pg_report_capacity_holders (lib/pro-gate-lib.sh:757-783) explains a “40-minute mystery” only on throttled stderr while SKILL.md:219 tells callers “poll THAT, not engine logs”; the phase enum has no generating state (bin/oracle-review.sh:655-657); the engine already emits recoverable=true/false “so automation cannot rot when wording changes” (bin/oracle-review.sh:179-183) — that discipline stops one field short; governor numbers are computed then discarded (lib:1330-1352). All citations verified against the live repo.
Rationale
pg_status() is a single verified write choke point that every consumer — the skill's poller, --status, the daemon, the oracle-reviewer agent, and idea 1's watcher — already reads. One additive schema change ships the entire observability slate at once, and every future consumer inherits it for free. It also finishes the job v0.33.0 started: the diagnosis for “why is no slot free” finally reaches the channel the documented contract points at.
Downsides
Schema growth needs discipline (additive-only, documented fields) and the heartbeat re-write must respect the existing atomic tmp+rename pattern. The prose paragraph in SKILL.md stays until callers migrate to next_action.

3. Nobody remembers to harvest: fleet-wide sweep + loss accounting

harvest-recovery Confidence 85% Complexity Low
Description
Add a --harvest-all sweep, run externally (cron or operator), that collects every outstanding reservation for the account in one pass — pg_report_capacity_holders already computes the list, and repeat harvests are documented free and idempotent. Replace SKILL.md's flat “wait ~10 min, then collect” with a payload-aware estimate (the engine already classifies diff size at submit). And log the expiry of a complete reservation as a distinct “spent-and-wasted” event — a paid-for Pro answer nobody redeemed — instead of the current undifferentiated TTL release.
Axis
harvest-recovery
Basis
direct: exit-9 grew 3.3% → 19.5% of all runs; “Repeat harvests are free: no Pro quota is spent” (SKILL.md:304-306); “Five runs sat in waiting-slot … while the ChatGPT account was idle” (v0.33.0 notes); SKILL.md juxtaposes “wait ~10 min” with “45–90+ minutes on a heavy payload (observed 65 min)” in the same section (253-256); pg_reservation_expire_if_stale (lib:798-816) logs no complete/generating distinction. All verified.
Rationale
One in five runs now ends in “remember to come back later.” v0.33.0 stopped uncollected reviews from starving other runs; nothing yet collects the review itself when the caller forgets, and a genuinely lost answer is currently invisible. An externally-triggered sweep is the legible version of this automation (the verifier flagged the self-spawning per-run variant as repeating the dropped OOM-self-heal pattern); a free, idempotent operation has no reason to be gated on caller memory.
Downsides
Sweep scheduling is per-box (cron here; launchd on macOS); it must serialize with live runs' locks and respect nonce binding when matching conversations to markers.

85%

4. Measure the queue and the spend honestly

slot-capacity-queue Confidence 90% Complexity Low
Description
Split the ledger's single secs into queue_secs + run_secs, stamped at phase transitions that already exist (waiting-pr-lock → waiting-slot → launching). Close out the charge-epoch skew family (a queued run can be charged ~80 min after its marker is minted — documented in a test comment). Publish an abandonment rate (how often generating reservations die vs convert). And add wall-clock-per-round to rounds/<key>.hist, --status, and the exit-12 message, so “4/4 rounds” reads “4/4 rounds, ~2.1h wall clock on this change.” Sequencing: build this first — it instruments the same phase-transition lines the stage-1 heartbeat touches, and it is the baseline ruler for the whole program: the before/after story for ideas 1, 5, and 7 (“poller invocations per wait went 65 → 1, queue p90 went X → Y”) only exists if the measurement fields land before the behavior changes do.
Axis
slot-capacity-queue (data foundation for queue-observability)
Basis
direct: RUN_START is stamped at preflight (verified line 697), before both lock waits at 1918/1975 — every duration percentile conflates queue-wait with generation; the ~80-min skew is documented at lib:1129-1134 and tests/engine.test.sh:1265-1268; a repo-wide grep found zero cost accounting; the operator had to report “$442.93” themselves. All verified.
Rationale
The system currently optimizes the one dimension it tracks (rounds) while the dimensions that actually hurt — queue time and session cost — are invisible to it. This is the cheapest survivor and the enabler for the rest: the verifier's own finding was that any ETA (“ready_by”) is systematically biased until queue and generation time are separated. Ship the split now and every later observability feature inherits clean data.
Downsides
Ledger schema change needs backward-compatible parsing in pro-gate-stats.sh; historical rows stay conflated (accepted — the split is forward-looking).
Confidence
90%
Complexity
Low

5. One supervisor per PR, not one ceremony per round

round-verdict-economics Confidence 75% Complexity Medium
Description
Stage 2, built on idea 1's --wait verb. Spawn one background subagent at round 1 that owns the entire §6 re-review arc and reports to the parent exactly once: SHIP, round-capped/escalate, or churn-braked. With --wait as its wait primitive, the supervisor's context stays small and mostly idle; its irreducible content is only what no primitive can absorb — round bookkeeping against the governor (headRefOid per round, trajectory reads via --status --json), fix-application policy, and disposition at stop. It is a plugin-side agent, not engine code: the engine stays a legible CLI, the orchestration intelligence lives in the agent file. The residual contract surface (exit codes, phases) that --wait doesn't delete gets a CI drift check across the remaining prose copies.
Axis
round-verdict-economics
Basis
direct: §6 repeats the full launch/poll/status ceremony up to 8× per PR (SKILL.md:381-430); “contract changes … both files must change in the same PR” (agents/oracle-reviewer.md:20); PR #1628 died specifically during a round-3 confirming pass; the governor already exposes machine-checkable termination conditions (base 3 / +1-per-shrink / ceiling 8 / 2-strike brake). Verified.
Rationale
Idea 1 fixes the single wait; this fixes the loop that multiplies it. The context burn in the incident wasn't one wait — it was the ceremony re-derived every round across 8 hours. A supervisor holding only the loop state (not the parent's whole task context) is the harness-native shape for that. Sequencing is forced: built without stage 1, the supervisor merely relocates poller fragility into a subagent; built on it, each round costs the supervisor one launch, one background --wait, one scoring turn.
Downsides
The supervisor must be crash-tolerant (its own death has to degrade to today's manual protocol, discoverable via --status); fix-application authority inside a subagent needs clear bounds; the daemon path keeps --wait-based blocking rather than subagent supervision.

75%

6. Churn Pareto first, fast tier second

round-verdict-economics Confidence 65% Complexity Medium
Description
Aggregate rounds/*.hist across the fleet (254+ gated changes, 737 spends) into a Pareto of which finding categories most often fail to shrink round-over-round — a pro-gate-stats.sh extension, pure reporting. Then, only if categories concentrate, stand up a cheap fast-tier pre-filter (lint/tests/Sonnet-level pass) targeted at exactly those categories before any Pro submission — the 2026 market's fast-shallow + slow-deep pairing, adopted on internal evidence rather than an external benchmark.
Axis
round-verdict-economics
Basis
direct: 32 of 36 recorded verdicts in the window were FIX-FIRST; “a Pro review of fresh code almost never comes back empty” (SKILL.md:383-385); the per-key .hist data (epoch, verdict, open P0/P1, resolved, still-present) exists and is never aggregated (verified: no rollup in stats/doctor). external: fast/deep reviewer pairing across the AI-review market (benchmark unverifiable from here — hence Pareto-first sequencing).
Rationale
Every FIX-FIRST round costs 20–160 min of wall clock and a slot someone else is queued behind. If a third of churn concentrates in categories a cheap pass can catch, the fast tier pays for itself immediately — and if the Pareto shows churn is irreducibly deep-model territory, you've spent one stats script to avoid building the wrong thing. The gate's terminal-rigor identity is untouched; what changes is what reaches it.
Downsides
Requires findings to carry a coarse category (today they're prose); the fast tier adds a moving part to the review path and its false-confidence risk must be framed as “pre-filter,” never “pre-approval.”
Confidence
65%
Complexity
Medium

7. Fair-share slot admission

slot-capacity-queue Confidence 55% Complexity High
Description
Replace pure arrival-order admission in the account-slot semaphore with a usage-decayed fair-share weight (SLURM's 2^(-usage/share), ~1-day half-life): a PR burning its 6th round today queues behind a PR requesting its 1st. Deprioritize heavy recent consumers gradually — never block them.
Axis
slot-capacity-queue
Basis
direct: the founding evidence for round budgets was “10–16 Pro slots on a SINGLE PR in one day … queue starvation for every other PR” (lib:1029-1030); verified that pg_lock_n has no priority concept — a churning PR and a first-time PR are admitted identically. external: SLURM fair-share + backfill.
Rationale
The codebase has twice validated the same governance shape — adaptive within a ceiling, earned by progress, collapsed on churn (concurrency ramp, round governor) — and the admission queue is the one scarce-resource site conspicuously missing it. This extends a pattern the team already trusts to the place the “queued behind another session's slot” complaint actually lives.
Downsides
Highest-risk survivor: priority logic in a multi-process flock/mkdir semaphore is subtle, starvation-freedom must be proven, and the win depends on how often true multi-session contention occurs (survivor 4's honest queue data should quantify that first). Build last, on evidence.
Confidence
55%
Complexity
High
