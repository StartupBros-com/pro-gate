ChatGPT-Web Bridge Adoption vs pro-gate

Three community projects were proposed as overlapping with pro-gate's oracle bridge. Analysis of their source found that none is adoptable wholesale — but a fourth project, surfaced during research, holds the exact signal pro-gate deferred a year of work on.

Grounding Context

Codebase Context

pro-gate runs a final-tier ChatGPT Pro code review of a GitHub PR. It shells out to the oracle CLI to submit a prompt into a logged-in Chrome session (bin/oracle-review.sh:1777-1785), and when oracle's own capture fails it falls back to its own raw-CDP client bin/cdp-salvage.mjs, which runs Runtime.evaluate on document.body.innerText over the tab's webSocketDebuggerUrl. Both paths therefore read rendered text.

Its design tenets are review-only authority (the gate never merges or writes code; a separate trusted fixer applies findings), fail-closed and recover-explicit, and — decisively for this analysis — the browser-driven model gets no filesystem or shell access. It receives a diff bundle plus a PR URL and returns text findings. The reason for driving a browser at all is that the Pro reasoning tier is web-UI-only, with no API.

Run state is flat files under $PRO_GATE_HOME keyed by repo-scoped PR identity: in-progress/ reservations, rounds/*.hist, conversation-urls/ memos, crossbound/ mis-bind proofs, write-once completed/, and an append-only ledger.jsonl. The project carries zero npm dependencies today.

Operational pain the candidates were measured against

For the twelve days to 2026-08-03, every clean run completed via salvage or harvest rather than primary capture — oracle's own capture succeeded on 0 of 22 runs on one day. The root cause is that oracle finalizes an assistant turn on the first visual settle, while Pro's UX is multi-phase: a preamble streams, briefly settles, then minutes of thinking follow before the real answer. A short preamble gets finalized as the review. An adversarial review concluded DOM-only proof is asymptotic rather than convergent and prescribed "network lifecycle completion, else fail closed" — and that branch was explicitly paused and never taken.

Separately, cross-bind incidents occurred twice in production where a harvested capture was genuinely another PR's review, because ownership was decided from a marker that rides the submitted prompt. The recorded lesson was "ownership requires the ANSWER, not the marker."

Orchestrator-verified probe

Installed oracle --version is 0.17.2. Grepping its shipped bundle for event-stream returns zero files, and CDP Network.* appears only in browser/index.js, projectSourcesRunner.js and the Gemini executor — never in the assistant-response capture path. oracle's completion detection is DOM-only in both the local fork and current upstream.

1

Read the conversation graph, not the rendered page

Replace "the page looks settled" as pro-gate's completion oracle with a structural contract evaluated against ChatGPT's own conversation message graph, fetched over REST. Rosetta's evaluateProTurnCompletion requires a terminal node with content_type: "text", recipient: "all", status: "finished_successfully", end_turn: true and finish_details.type: "stop" that is a graph descendant of a reasoning_recap node carrying reasoning_status: "reasoning_ended" — rejecting the candidate if any is_reasoning node is a sibling or graph-incomparable branch, and failing closed with an explicit INCOMPLETE Pro turn rather than guessing.

The same fetch also carries metadata.turn_exchange_id, which rosetta keys ownership on. That is a graph field, not a substring in rendered text, so it settles cross-bind at the same time and by the same mechanism. Operationally this makes in-run polling the normal completion path and returns harvest to being genuine crash recovery — though harvest must stay, because long runs also stall for reasons unrelated to completion timing.

Basis
direct: pro-final.ts:49-52 states plainly that "end_turn, finished_successfully, stream terminators, and create_time ordering are not completion proof. Pro can emit several short progress texts carrying both flags and then resume reasoning" — an independent rediscovery of pro-gate's own preamble bug. Ownership keys on message.metadata?.turn_exchange_id !== turnExchangeId, confirmed verbatim. Against this, the orchestrator probe confirms oracle 0.17.2 ships zero event-stream references.
Rationale
pro-gate's own postmortem prescribed exactly this signal class and then paused the branch for scope. A tested, MIT-licensed reference implementation removes the reason the branch stayed paused. Because the fix replaces the authority rather than adding another heuristic, the stall watchdog, salvage and nonce guard become backstops instead of the load-bearing path.
Downsides
It fixes two of the three bug classes it is tempting to bundle — VERDICT extraction still needs a text scan, because VERDICT: is pro-gate's own prompt convention, not a ChatGPT API field. It also binds pro-gate to an undocumented internal response shape that can change without notice, so it needs its own fail-closed path. New glue is required to capture turn_exchange_id at submission time.

Vendor two zero-dependency files at a pinned rev

Take rosetta as source, not as a runtime dependency and not as a transport replacement. Copy src/pro-final.ts and src/sse.ts into pro-gate at a pinned upstream revision, with attribution, and leave oracle owning launch, authentication, navigation, model selection and submission. This is the narrowest form of idea 1 that still gets the whole benefit.

Vendored code drifts silently unless someone diffs the pinned rev periodically, and pro-gate inherits maintenance of a wire format it does not control. Attribution and license notice must be handled properly in a distributed tool.

3

Adopt the REST leg; decline the live-CoT WebSocket

Rosetta has two capture legs, and they are separable. The REST poll of /backend-api/conversation/<id> reads the same conversation a signed-in human sees rendered. The second leg opens its own WebSocket to wss://ws.chatgpt.com and reads live chain-of-thought frames the UI never displays. Take the first; do not take the second.

Basis
direct: verification confirmed evaluateProTurnCompletion takes only a ConversationMapping — a REST JSON payload — and never references sse.ts or anything WebSocket-related. The two legs are provably separable in code. reasoned: OpenAI's terms bar "any method to extract data from the Services, including web scraping … other than as permitted through the API." Reading content that has no rendered-UI equivalent sits further from the "automating what a human sees" reading than DOM scraping does, on an account pro-gate already treats as a scarce shared resource.
Rationale
The whole reliability argument for idea 1 rests on the completion contract, and that contract is fed entirely by REST. Adopting the WebSocket leg would add account risk for no capture benefit. Making this an explicit boundary now stops it being quietly crossed later during implementation.
Downsides
The ToS reading is forum-sourced rather than adjudicated, so the distinction is a judgment call rather than a settled legal line — and pro-gate's existing DOM extraction already sits on the same spectrum. Declining the WebSocket also gives up live progress visibility during long reasoning runs.

4

Treat the four projects as a supply chain, not a shortlist

The question as posed — cherry-pick, adopt, run side-by-side, or consolidate — assumes the projects compete for one slot. They do not. Each owns a different subsystem, and no two solve the same problem, so the right output is four separate verdicts rather than one vote.

Basis
reasoned: cross-referencing each project's own description shows no overlap in the problem solved: rosetta owns capture and completion; devspace owns tool exposure, widgets and working-tree checkpoints; local-mcp owns OS-level sandboxing of local execution; codex-chatgpt-web owns an interactive multi-turn backend with its own token-ceiling and liveness machinery. Only rosetta's subsystem is one pro-gate is currently doing badly.
Rationale
This reframing is what makes the other six ideas coherent rather than competing. It also explains why "consolidate into a meta-skill" is the wrong shape here: there is no shared surface to consolidate, only one component to import and three verdicts to record.
Downsides
Four separate verdicts are more work to communicate than one, and the framing risks implying every project must yield something — three of the four yield nothing pro-gate should ship.

5

Record the standing decline of local filesystem/shell exposure

Write a decision record, in the same docs/solutions/conventions/ shape as the existing ship-the-legible-core convention, stating that exposing local filesystem or shell to the browser-driven model is out of scope for pro-gate — so the next trending repo in this genre does not restart the evaluation from zero. This is the fourth such project in a single research pass.

Ground the decline on the tenet, not the platform claim

The tempting justification — that Pro-tier accounts cannot use write-capable MCP at all — is external, unverified, and contradicted by devspace's own README documenting ChatGPT web plus custom connectors working over a tunnel. The durable justification needs no external claim: both projects' own docs confirm arbitrary shell and filesystem access for the driving model, which directly contradicts pro-gate's stated tenet. A decision record that cites the unverified platform claim will rot the moment OpenAI changes tiering.

Basis
direct: devspace's docs/security.md:86-87 states shell commands "can do what your user account can do," and the same docs say the tunnel URL should not be treated as a secret — leaving one shared static password as the only barrier. local-mcp's session_id is validated for character legality rather than secrecy and is designed to be pasted into a chat prompt, and /permissions yolo makes unsandboxed shell silent. Against these, pro-gate's own tenet is that the browser-driven model gets no filesystem or shell access.
Rationale
pro-gate already has a precedent for recording a considered "no": three automations were each built, gate-reviewed over two to three rounds, then dropped when new real problems kept surfacing. Recording this decline once, with the evidence attached, is far cheaper than re-litigating it per trending repo — and it prevents the review effort being spent on devspace's genuinely well-built parts under a premise that does not apply.
Downsides
A standing "no" can calcify: if ChatGPT's connector model or pro-gate's own scope changes materially, the record needs revisiting rather than citing. It should name the tenet it depends on so the revisit trigger is obvious.

Token-aware payload bounding with periodic recalibration

pro-gate decides whether a diff will fit by counting lines. Replace that with a token estimate measured against an empirically discovered transport ceiling, and re-measure the ceiling periodically rather than hardcoding it — the real wall drifts the same way selectors drift.

Basis
direct: bounding today is purely DIFF_LINES against three line-count environment variables, and the code's own comment concedes the proxy is weak: "984-1402-line diffs complete in 12-21 min; a ~10k-line diff reasoned 65 min then had to be harvested." external: codex-chatgpt-web binary-searched the actual limit rather than assuming it — CHATGPT_LUNA_BROWSER_INPUT_TOKEN_BUDGET = 28_000, annotated as empirically measured, with the same payload shape accepted at 25,400 and 28,547 estimated tokens but rejected at 32,283, and identified as a browser transport boundary rather than a model context limit. external: the structure matches Path MTU Discovery: probe an undocumented ceiling rather than assume one.
Rationale
Line count and token count diverge sharply by content — dense minified diffs versus sparse source — so the current threshold both wastes slots cooking payloads that would have fit and lets doomed payloads cook anyway. Since each mistake costs a real Pro slot on a serialized single-account resource, a preflight estimate converts a blind spend into a cheap rejection.
Downsides
Needs a tokenizer pro-gate does not currently carry, and codex-chatgpt-web's specific 28k figure is for a different tier and will not transfer as a constant. The calibration probe itself costs slots to run. The correlation is unproven for pro-gate's own traffic, so this warrants an instrumented measure-first pass — log token estimate alongside line count for a while — before any threshold changes.

7

A separate consult skill on rosetta's capture layer

If interactive Pro consults are wanted — asking a design question mid-session, sanity-checking an approach — build that as its own small skill on the same vendored capture layer, deliberately outside pro-gate's authority model. Do not add an interactive mode to the review gate.

Basis
direct: pro-gate's tenet is review-only authority, and its reviewer agent is instructed never to edit files, apply patches, stage or commit. Its entire engineered-around-failure list — stall watchdog, nonce guard, harvest, round governor — assumes a bounded, single-shot, text-only exchange. external: codex-chatgpt-web demonstrates real demand for Pro-as-interactive-backend, which is its whole product.
Rationale
Folding interactive consulting into the review gate would blur the one boundary that keeps pro-gate's failure modes tractable. A separate skill also lets the vendored capture layer be exercised on a low-stakes surface before it is trusted inside a terminal merge gate.
Downsides
Speculative — no demand for this has been demonstrated in pro-gate's own usage, and it should be sequenced strictly after ideas 1 through 3 prove the capture layer works. Note that building it on codex-chatgpt-web's turn machinery instead would be a much larger undertaking: that code is Electron- and CDP-entangled across thousands of lines, not portable like rosetta's two files.
