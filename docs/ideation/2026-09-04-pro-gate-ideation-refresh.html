Grounding Context

Codebase Context

pro-gate is a final-tier pull-request review gate that drives a logged-in ChatGPT Pro web session over the Chrome DevTools Protocol, then routes findings to a coding-agent fixer. The plugin (skill plus relay agent) ships through the HOV marketplace; the runtime (engine, library, daemon, salvage helper, doctor, stats) installs separately as a version-matched archive. The engine is about 4,200 lines of bash, the library about 3,000, the engine test suite about 5,900.

What shipped between the last ideation docs and today. v0.34.0 split ledger durations at slot acquisition and added wall-clock per round. v0.35.0 recovered finished reviews from stale tabs. v0.36.0 introduced review-decision/v1: one typed next action, checked by contract identity on the skill, relay, daemon, and doctor, with a single named product choice as the only prompt. v0.37.0 unified the attempt lifecycle behind one canonical snapshot, added marker-addressed terminal dispositions, and made round history advisory by default. v0.37.2 through v0.38.2 added proof-backed supersession so an old-head or merged review releases capacity without a refund. v0.38.0 made bundle-only input the default. v0.39.1 added --brief, a swappable task body that is deliberately unexposed through the skill and relay. v0.40.0, today, records a closed-enum failure reason on every failed ledger row.

What was closed. The blocking --wait verb with heartbeat and next-action fields (PR #89, issue #88) was closed unmerged on 2026-09-01 because it added a second controller without adding submit, collect, or recover capability. The ChatGPT-web bridge research (PR #79, the rosetta completion contract) was closed as stale once the lifecycle findings had shipped. The connector-isolation branch was superseded by input policy.

What is still open. Issue #109: a current-head, exact-owned conversation that never emits a verdict pins a slot indefinitely. The root cause found was a synthetic WEB:<uuid> placeholder persisted as the marker's authoritative conversation URL, plus a real-id owned-incomplete case. The issue's guidance forbids any terminalizer from age, TTL, repeated missing verdicts, or an absent spinner alone, and blocks the fix on a turn-scoped terminal predicate verified across bounded fresh renders. Four reproductions exist.

Decisions made outside this repo. The per-PR supervisor from the August ideation was built in dotfiles as a bash wrapper, pro-gate-loop.sh (PR #986): CI wait, typed query, closed action table, a fresh fixer per round, a flat four-round cap, a 30-second poll. The dotfiles umbrella #849 named two Pro capacity lanes, enabled the daemon for a measurement week that ends 2026-09-09, shipped the send-to-Pro primitive as --brief, and withdrew the tunnel-based async lane because the GitHub connector already covers that corpus. The operator's standing instruction is to keep this work in plain operational language: agents take a knowable safe next step without asking routine permission, never repeat the same review without new evidence, and merge only after a verified SHIP.

Still binding from the prior docs

No raising or softening of the round ceiling as a quota. No daemon dollar budget for Pro rounds. No exit-7 as a durable ticket. No multi-PR multiplexing in one conversation. No self-spawning per-run auto-harvester. No protocol compiler or manifest. No autonomy envelope, per-finding ledger, or one-shot evidence substitution. No terminalizer from age, TTL, missing verdict, or absent spinner alone. --brief stays unexposed through the skill and relay.

Past learnings

Ship the legible core and let the gate decline fragile automation: repeated FIX-FIRST across two or more rounds on one feature is a signal to drop it, and for a credentialed distributable a clear message plus one manual command beats automation. Separate lifecycle, applicability, capacity, and input trust: one canonical attempt snapshot, capacity as a query over proof, exact recovery instead of retry-as-diagnosis, and evidence-gated residuals left open rather than forced into a timeout. An appended prompt contract is cooperative, not enforced. A staged release tag can predate a later fix on the same version.

External context

Review-gate yield has a vocabulary already: Meta's RADAR escalates only high-risk changes to the expensive tier and reports a 35 percent cut in median review wall time; SWE-PRBench puts AI reviewers at 15 to 31 percent detection with 19 to 42 percent false positives; CodeHerder's review-debt dashboards track p50 and p90 latency, reject-loop depth and cap, and first-pass rate; Span names turn yield. Job systems distinguish never-claimed from claimed-then-died orphans with separate clocks (AWS Step Functions), mark dead-letter rows terminal so a sweep stops re-picking them (Cabana issue 23), and run a scheduled finalize-reconciler distinct from a one-time sweep (Canopy). Kubernetes keeps liveness, completion, and orphan detection as three questions. For completion of a chat turn, browser test guidance converges on asserting an explicit completion-state attribute rather than a hidden spinner or a timeout; ChatGPT's own backend carries a per-message status plus an end-turn flag, but the closest prior art on this product, rosetta, rejects end-turn and stream terminators as proof for the preamble-then-resume behavior pro-gate already hit. Large-diff review at scale is chunked (Qwen Code), two-staged (GitLab Duo), or split recursively (Datadog); stacked review can lose the integration reviewer.

1. The legible core of #109: visible, revocable, swept — before terminal Stuck and verdict-less runs Confidence 88% Complexity Medium

Description
Four moves that need no new termination authority. First, parity on the sweep: the plain still-generating harvest branch re-writes the reservation and exits 9 forever, while the unbindable-capture branch a few hundred lines earlier already gates on the reservation TTL plus a run of confirmed-absent probes spaced by an interval. Give the plain branch that same two-factor gate. Second, make a remembered conversation URL prove itself: today a memo is exempt from the foreign-marker blacklist and the per-URL render cap forever, so a placeholder page titled "ChatGPT" keeps being re-rendered and reported as generating on every pass. Validate the URL cheaply each pass and let the existing provenance-revocation call fire on a page that is not a conversation, not only on a foreign one. Third, stop collapsing the salvage probe's classification: it already distinguishes owned-incomplete, still-generating, target-url-drift, stale-terminal, and unbindable-ambiguous, then reports one word. Surface the class with age, probe count, and remaining TTL in status, and persist it as a closed-enum stall class on in-progress and harvest ledger rows, the way v0.40 did for failed rows. Fourth, hand the aging view to the weekly read (idea 2).
Axis
Stuck and verdict-less runs
Basis
direct: the rc=3 harvest branch at bin/oracle-review.sh:2657-2661 writes the reservation and calls pg_finish 9 with no TTL or miss check, while the unbindable branch at :2600-2607 does; lib/pro-gate-lib.sh:1546-1562 states "TTL is a precondition for recovery exhaustion, never terminal proof by itself" and the miss rule requires a configurable number of confirmed-absent probes; bin/cdp-salvage.mjs:44-49 "A remembered URL is authoritative for its marker: it is exempt from the foreign-marker blacklist and from the per-URL render cap"; bin/cdp-salvage.mjs:1196-1199 collapses the probe classification to generating; the state directory holds 8 in-progress markers, the oldest 80 hours, and 4 memos pointing at WEB: placeholders; issue #109 comments of 2026-08-31 and 2026-09-01. All citations verified by a fresh-context reviewer.
Rationale
Every #109 reproduction was invisible until an operator grepped stderr and listed a state directory. The issue reporter's own first suggestion was to validate before remembering and make authority revocable. This is the part of the fix that needs no unproven completion predicate, so it can ship first and keep paying even if the predicate never lands. It also attacks the 6.56 harvest passes per collected review at the point where a pass is wasted, and it leaves the "no terminalizer from age or TTL alone" rule intact, because the sweep it extends already demands confirmed absence, not elapsed time.
Downsides
The parity sweep must be proven never to release a live review; the confirmed-miss probes are the safeguard, and the engine tests that today assert indefinite re-sampling as correct must be rewritten deliberately rather than deleted. The stall class adds a ledger field, which is why idea 6 asks for a ledger schema. None of this closes the current-head owned-incomplete case on its own; that still needs an evidence-gated completion predicate, discussed under rejection A.

2. A native weekly yield row, in time for the measurement week The weekly read Confidence 90% Complexity Low

Description
Add a weekly mode to pro-gate-stats.sh that prints a handful of lines from data already written every round. A churn Pareto from the round history files: rounds per merged change, and which changes fail to shrink round over round. The failure-reason mix, with the floor-plus-week-over-week trend warning the dotfiles lane report already proved on lock timeouts. Turn yield, meaning clean verdicts per slot spent, per diff-size band. Abandonment with two clocks, borrowed from job schedulers: attempts never observed generating versus attempts observed generating and then dark, and how many passes each cost. Under-submission aging: in-progress markers past a threshold and memos still pointing at placeholders. The dotfiles lane report then reads these lines instead of re-deriving them from raw rows.
Axis
The weekly read
Basis
direct: the stats script's header at bin/pro-gate-stats.sh:4-5 lists the ledger fields and still omits reason and detail after v0.40.0; the script never references the rounds directory; the round history format at lib/pro-gate-lib.sh:1803-1806 is written every round and aggregated nowhere; the dotfiles lane report prints "operator-attention minutes: not measured"; the ledger shows runs per PR rising from 2.92 to 3.96 and one PR at 50 rows. external: CodeHerder's review-debt metric vocabulary; Span's turn yield; AWS Step Functions' two orphan clocks.
Rationale
The measurement week set up under the dotfiles umbrella ends on 2026-09-09 to answer whether Pro capacity is the bottleneck, and nothing in this repo prints a number that answers it. Reporting is the cheapest survivor and the ruler for every other one: without it, ideas 1, 5, and 7 have no before-and-after. It refreshes the churn Pareto from August with worse numbers and closes the abandonment residual left by the ledger split.

3. Decision v1.1: the contract carries the facts callers re-derive Where the loop lives Confidence 80% Complexity Medium

Description

The governor object today exposes a single boolean; add the trajectory the engine already computes in one place, meaning base, earned, ceiling, streak, and whether the policy mode is advisory or enforced. The dotfiles loop script can then enforce the runtime's numbers instead of its own flat four, but it must keep a cap of its own while rounds are advisory by default, because today that cap is the only limit that binds.

5. A size-aware yield ladder for the large-diff band Review yield per slot Confidence 70% Complexity Medium

Description
Three steps on one evidence chain, each gated on the previous one's numbers. First, a report-only yield-by-size view in the stats script, which is also the ruler. Second, size the collection timeout to the diff: the twenty-minute value that operators and the skill copy from nine hint strings is fixed regardless of payload, and a quarter of all still-generating rows end at exactly that boundary; let the runtime supply a collect timeout from the size bucket's historical post-slot duration instead. Third, only if the band over six thousand lines still loses after the window is fixed, trial the cheapest structural option, risk-ordered hunks in a single payload, before a two-turn pre-scan in one conversation with one final verdict. The cook-and-harvest thresholds themselves, set from one July anecdote, get re-derived from the same view.

7. Admission tells the truth at second zero, then substitutes fairly Review yield per slot Confidence 55% Complexity Low, then High

Description
Two steps, the second gated on evidence from idea 2. First, the engine already builds two distinct messages when capacity runs out, one for slots held by uncollected finished reviews and one for slots genuinely busy, but it builds them only after the lock-wait loop has already timed out, up to forty minutes later. Compute that diagnosis before entering the loop and, when capacity is zero for the whole wait class, return a typed no-capacity decision immediately, then re-check briefly so a slot freed a few seconds later is not missed. Second, if the weekly queue numbers show real contention rather than harvest churn, add ground-delay-program style substitution: a caller's own oldest uncollected attempt outranks its own fresh retry for the next freed slot, total capacity stays fixed, and no caller gains priority over another's ceiling. This is the August fair-share idea with a named, production-tested mechanism and the same posture as before: build last, on evidence.
Axis
Review yield per slot
Basis
direct: the slot deadline is set at bin/oracle-review.sh:3362, the loop exits at :3386 or :3397, and the two-message diagnosis at :3400-3406 runs only inside the failure branch afterward, as the fresh-context reviewer confirmed; 59 lock timeouts since 2026-08-17; the lanes doc measured a 614-second median queue and 19 timeouts in two days at four-of-four concurrency. external: FAA ground delay programs' ration-then-compress substitution.
Rationale
Every caller that times out already burned that wall clock for a fact the engine could have stated at once. The substitution step gives the fair-share gap, open since 2026-08-17, a concrete algorithm without touching the round ceiling or multiplexing conversations.
Downsides
"Genuinely zero" must be re-checked; a slot can free three seconds after the answer. Priority inside a multi-process lock is subtle, starvation-freedom must be proven, and the queue data so far says contention is bursty, not constant, so the second step may never earn its cost. Lowest confidence in the set for that reason.
