# v0.56.0

## Highlights

- A review whose send never reached a ChatGPT conversation now frees its slot within minutes instead of about six hours. The round still counts.

## Upgrade

Update the plugin and runtime together to v0.56.0. Nothing else to do. An older runtime ignores the new kind of attempt record, so rolling back is safe.

## Details

Sometimes Oracle clicks Send, but the prompt never shows up in the conversation. After at least 60 seconds of waiting, Oracle gives up with `prompt-commit-timeout`, and its tab is still on the ChatGPT landing page. Because Send was clicked, pro-gate cannot prove the prompt never reached ChatGPT, so the round stays charged. What went wrong is what came next:

1. It waited up to 150 seconds to reattach to an Oracle session that had no conversation.
2. It treated the review as possibly still generating, which stretched the final browser scan from the normal window to the full review budget, 62 minutes by default.
3. It exited with the attempt still marked "fate unknown". Every later caller was told to recover it, and the slot stayed held until the six-hour reservation limit ran out.

On 2026-09-26, pro-gate #227 lost 6h49m to this in round 1 and 4h22m in round 8.

A check of every Oracle session on this host that ended with `prompt-commit-timeout` (129 of them) shows the tab's URL is what separates the two cases. All 64 sessions where the tab was inside a conversation went on to produce a review; those are Oracle's own false alarms. Of the 65 where the tab never reached a conversation, only one ever produced a review, and in that one the whole prompt was still sitting in the composer and went out late. So pro-gate also requires an empty composer, which all 10 such timeouts since 2026-09-07 had. The other signals Oracle records (a new turn, a stop button, an assistant reply) read the same in both groups, so they count only as evidence against this outcome.

pro-gate now reads the same exact, digest-verified Oracle session record its refund proof uses. When every attempt was either never sent or sent with no conversation to show for it, and the final scan is clean with no remembered conversation URL, no throttle and a stable browser, it:

- skips the reattach;
- keeps retries suppressed, but uses the normal scan window;
- records the attempt as finished (`recovery-exhausted`, proof `no-conversation-after-send`) and releases the slot. The round stays charged. The next typed decision can grant a fresh round straight away.

The ledger records these rounds with the new reason `no-conversation`.

This release claims only that the send produced no ChatGPT conversation during Oracle's commit check and the final scan. It does not claim the prompt never reached ChatGPT, and it refunds nothing. If a conversation or its ID ever shows up, if the tab URL points at a conversation or was not recorded, if the prompt is still in the composer, or if the session record does not belong to this run, today's charged path applies unchanged.

The Oracle-side cause, a prompt that is not where Send reads it, is separate work. Attempts killed by the watchdog keep their unknown fate.
