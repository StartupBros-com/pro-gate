# v0.41.0

## Highlights

- Reviews now wait long enough to finish: 60 minutes for a fresh review and 45 per collection pass, sized from real review times, so one pass usually collects instead of six.
- A busy reservation guard no longer leaks a file handle when it loses the race, and without `flock` it clears a guard left by a crashed process instead of stalling.
- The daemon now checks review decisions with the same validator the test suite exercises, so it can no longer drift from the skill and relay unnoticed.

## Upgrade

Update the plugin and runtime together to v0.41.0.

**One constraint, and it applies only to hosts without `flock` (in practice, macOS): do not run the previous runtime alongside this one.** The old reservation guard wrote no owner marker, so this version cannot tell one of its directories from an abandoned one. Stop the old runtime first; a host with `flock` is unaffected.

If you set `--timeout` explicitly, or export `PRO_REVIEW_ENGINE_TIMEOUT` for the daemon, your values still win; the new defaults apply only where nothing was set. Note that leaving `PRO_REVIEW_ENGINE_TIMEOUT` **unset is now meaningful**: the daemon then lets each engine call size itself (60 minutes fresh, 45 for a recovery), whereas setting it forces that one value onto both.

New optional settings, all documented in `.env.example`: `PRO_GATE_TIMEOUT` and `PRO_GATE_HARVEST_TIMEOUT` override the two waits machine-wide, and `PRO_GATE_DIRLOCK_ORPHAN_GRACE` tunes how long an unmarked no-`flock` guard directory must sit before a reclaimer may remove it.

`PRO_GATE_LOCK_WAIT`'s default rises from 2400 to 3900 seconds. It is how long a queued review waits for the run ahead of it, and 40 minutes no longer covered a review that may now legitimately take 60 — a queued run was expiring while the run it waited for was still working. Explicit values are unchanged.

## Details

Since mid-August the ledger recorded 6.56 collection passes for every review it eventually collected, and 40 percent of all rows ended as "still generating, collect later". The cause was arithmetic, not the model. Measured over clean reviews since 2026-08-17, the median review took 22 to 48 minutes after acquiring a slot depending on diff size, and the slowest tenth took 40 to 62 minutes. The fresh-review default was 30 minutes, below the median for large diffs, and every recovery hint told callers to collect with a 20-minute wait, so a long review was cut off once and then re-checked in windows shorter than the time it still needed.

One flag, `--timeout`, governs both waits. Its default is now 60 minutes for a fresh review and 45 minutes for `--harvest` and `--recover`, the hints print the 45-minute value, and the skill and relay pass the same numbers. The daemon passes the 60-minute wait for a fresh review and, unless `PRO_REVIEW_ENGINE_TIMEOUT` is set, lets the engine size a recovery itself, so `PRO_GATE_HARVEST_TIMEOUT` reaches unattended collection too. Both stay well inside the six-hour reservation window, and neither changes when a review may be declared finished: a pass that runs out of time still leaves the review recoverable by marker, exactly as before.

The reservation guard, which serializes reservation writes against slot acquisition, opened a file descriptor and then returned failure without closing it whenever another process held the guard for more than ten seconds. Under contention that leaked one descriptor per attempt for the life of the process. It now closes the descriptor on a timed-out acquire. The no-`flock` fallback used on macOS can recover a guard left by a dead process, and a failed acquire no longer leaves the guard pointing at a directory this process did not own. The holder's identity is a marker file inside the guard directory, named after the shell that actually holds it, so a guard taken inside a command substitution is not mistaken for dead when its parent exits. Recovery and release only ever unlink a marker by its exact name and then remove the directory with `rmdir`, which fails while any other marker is present. That is what stops two waiters that both saw a dead owner, or a removal orphaned by a holder that died mid-release, from deleting a guard another process has since re-created. On a host without `flock`, do not run the previous runtime alongside this one, because the previous guard carried no marker.

The daemon validated saved review decisions with a private copy of the contract schema, which made it the one consumer of the closed action table that no conformance test covered. That validator now lives in the shared library as `pg_review_decision_envelope_valid`, the daemon calls it, and the conformance suite proves it accepts every envelope the runtime emits for the frozen corpus and rejects a swapped action, an injected blocking-wait field, a foreign contract digest, and a symlinked file. The same suite now also checks that the skill and relay carry the sized timeouts, so the churn this release removes cannot creep back through a stale hint.

## Fixed

- The default review wait was shorter than the median large review, and the default collection wait was shorter still, forcing repeated collection passes.
- A contended reservation-guard acquire leaked a file descriptor on every timeout.
- The no-`flock` reservation guard could stall on a directory left by a dead process and could release a guard it did not own.
- The daemon's decision validator was a private schema copy outside conformance coverage.
- The queued-review wait (`PRO_GATE_LOCK_WAIT`, 40 minutes) was shorter than the review wait it queues behind, so a queued run gave up while the run ahead of it was still legitimately working.
- One operator-facing harvest hint, printed by the library rather than the engine, still told callers to collect with the old fixed 20-minute wait. The check that guards this read only the engine; it now reads every shipped shell file, and the wait has a single shared definition.
- Without `flock`, a reclaimer could remove a guard directory a live contender had just created and not yet marked. That contender's marker then landed in a replacement directory another shell already held, and both believed they held the guard. An unmarked directory is now only reclaimed once it is older than `PRO_GATE_DIRLOCK_ORPHAN_GRACE`, and an acquire that finds a second marker stands down instead of reporting a hold.
- Guard reclamation identified owners with `kill -0` alone, so a recycled pid read as a live owner and wedged the guard permanently. Markers now carry the owner's process start time, and liveness requires both to match.
- A `mkdir` that failed for any reason other than contention — a missing or unwritable parent — was treated as a successful reclaim, so the guard retried with no sleep and no counter increment and spun at 100% CPU, ignoring its own wait bound.
- On a shell without `BASHPID` (stock macOS `bash` 3.2, which is also the shell that has no `flock`), the owner pid silently fell back to `$$` and reinstated the very defect `BASHPID` was introduced to fix.
