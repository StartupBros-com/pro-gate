# v0.41.0

## Highlights

- Reviews now wait long enough to finish: 60 minutes for a fresh review and 45 per collection pass, sized from real review times, so one pass usually collects instead of six.
- Those waits are finally configurable in practice. The shipped skill and relay used to hardcode the timeout, which made the new settings unreachable on the path most reviews take.
- The daemon now checks review decisions with the same validator the test suite exercises, so it can no longer drift from the skill and relay unnoticed.

## Upgrade

Update the plugin and runtime together to v0.41.0. Nothing else to do.

If you set `--timeout` explicitly, your value still wins; the new defaults apply only where nothing was set. Note that leaving `PRO_REVIEW_ENGINE_TIMEOUT` **unset is now meaningful**: the daemon then lets each engine call size itself (60 minutes fresh, 45 for a recovery), whereas setting it forces that one value onto both.

New optional settings, documented in `.env.example`: `PRO_GATE_TIMEOUT` and `PRO_GATE_HARVEST_TIMEOUT` override the two waits machine-wide.

`PRO_GATE_LOCK_WAIT`'s default rises from 2400 to 3900 seconds. It is how long a queued review waits for the run ahead of it, and 40 minutes no longer covered a review that may now legitimately take 60 — a queued run was expiring while the run it waited for was still working. Explicit values are unchanged.

## Details

Since mid-August the ledger recorded 6.56 collection passes for every review it eventually collected, and 40 percent of all rows ended as "still generating, collect later". The cause was arithmetic, not the model. Measured over clean reviews since 2026-08-17, the median review took 22 to 48 minutes after acquiring a slot depending on diff size, and the slowest tenth took 40 to 62 minutes. The fresh-review default was 30 minutes, below the median for large diffs, and every recovery hint told callers to collect with a 20-minute wait, so a long review was cut off once and then re-checked in windows shorter than the time it still needed.

One flag, `--timeout`, governs both waits. Its default is now 60 minutes for a fresh review and 45 minutes for `--harvest` and `--recover`, and every operator-facing hint renders that value from one shared definition rather than a literal copied into each site.

The engine treats any `--timeout` it receives as final, which made a second defect worse than it looked: the skill, the relay and the daemon all supplied one unconditionally, so the configured default could never apply on the paths that matter. All three now pass a timeout only when one was actually configured, and the conformance suite checks for its absence rather than its presence. Both stay well inside the six-hour reservation window, and neither changes when a review may be declared finished: a pass that runs out of time still leaves the review recoverable by marker, exactly as before.

The reservation guard, which serializes reservation writes against slot acquisition, opened a file descriptor and then returned failure without closing it whenever another process held the guard for more than ten seconds. Under contention that leaked one descriptor per attempt for the life of the process. It now closes the descriptor on a timed-out acquire, honours `PRO_GATE_RESERVATION_GUARD_WAIT`, and clears its directory variable on failure so a later release can never remove a guard this process does not own.

The daemon validated saved review decisions with a private copy of the contract schema, which made it the one consumer of the closed action table that no conformance test covered. That validator now lives in the shared library as `pg_review_decision_envelope_valid`, the daemon calls it, and the conformance suite proves it accepts every envelope the runtime emits for the frozen corpus and rejects a swapped action, an injected blocking-wait field, a foreign contract digest, and a symlinked file. Those rejection checks now score an explicit return code and assert the validator is callable first, so a missing or renamed validator fails the suite instead of passing it silently.

## Fixed

- The default review wait was shorter than the median large review, and the default collection wait was shorter still, forcing repeated collection passes.
- The shipped skill and relay hardcoded `--timeout`, so `PRO_GATE_TIMEOUT` and `PRO_GATE_HARVEST_TIMEOUT` never applied on the path most reviews take. The check meant to guard this required the hardcoded values, so it enforced the bypass rather than catching it.
- The daemon sent a fixed 60-minute wait on every fresh review it launched, with the same effect, and now matches what it already did for recovery.
- The queued-review wait (`PRO_GATE_LOCK_WAIT`, 40 minutes) was shorter than the review wait it queues behind, so a queued run gave up while the run ahead of it was still legitimately working.
- One operator-facing harvest hint, printed by the library rather than the engine, still told callers to collect with the old fixed 20-minute wait. The check that guarded this read only the engine; it now reads every shipped shell file, and the wait has a single shared definition.
- A contended reservation-guard acquire leaked a file descriptor on every timeout, and a failed acquire left its directory variable pointing at a guard it did not own.
- The daemon's decision validator was a private schema copy outside conformance coverage, and four of its rejection checks passed identically whether the validator existed or not.

## Not in this release

Self-healing the no-`flock` reservation guard — reclaiming a directory whose owner has died — is tracked separately. It needs dead-owner detection that tolerates pid reuse, a grace so a live contender is not reclaimed between its `mkdir` and its marker, and removal that can never touch a replacement directory. Each of those was gotten wrong at least once during review, so it ships with the related `pg_lock` / `pg_lock_n` work (#152, #155) where one hardened helper can serve all three call sites instead of two divergent ones. Until then that path behaves exactly as v0.40 did: a directory left by a killed process makes later acquires wait out their bound and fail, which is a stall rather than a mutual-exclusion failure.
