# v0.41.0

## Highlights

- Reviews now wait long enough to finish: 60 minutes for a fresh review and 45 per collection pass, sized from real review times, so one pass usually collects instead of six.
- A busy reservation guard no longer leaks a file handle when it loses the race, and without `flock` it clears a guard left by a crashed process instead of stalling.
- The daemon now checks review decisions with the same validator the test suite exercises, so it can no longer drift from the skill and relay unnoticed.

## Upgrade

Update the plugin and runtime together to v0.41.0. Nothing else to do. If you set `--timeout` explicitly, or export `PRO_REVIEW_ENGINE_TIMEOUT` for the daemon, your values still win; the new defaults apply only where nothing was set. Two new optional settings, `PRO_GATE_TIMEOUT` and `PRO_GATE_HARVEST_TIMEOUT`, override the defaults machine-wide.

## Details

Since mid-August the ledger recorded 6.56 collection passes for every review it eventually collected, and 40 percent of all rows ended as "still generating, collect later". The cause was arithmetic, not the model. Measured over clean reviews since 2026-08-17, the median review took 22 to 48 minutes after acquiring a slot depending on diff size, and the slowest tenth took 40 to 62 minutes. The fresh-review default was 30 minutes, below the median for large diffs, and every recovery hint told callers to collect with a 20-minute wait, so a long review was cut off once and then re-checked in windows shorter than the time it still needed.

One flag, `--timeout`, governs both waits. Its default is now 60 minutes for a fresh review and 45 minutes for `--harvest` and `--recover`, the hints print the 45-minute value, and the skill, relay, and daemon pass the same numbers. Both stay well inside the six-hour reservation window, and neither changes when a review may be declared finished: a pass that runs out of time still leaves the review recoverable by marker, exactly as before.

The reservation guard, which serializes reservation writes against slot acquisition, opened a file descriptor and then returned failure without closing it whenever another process held the guard for more than ten seconds. Under contention that leaked one descriptor per attempt for the life of the process. It now closes the descriptor on a timed-out acquire. The no-`flock` fallback used on macOS gained the same dead-process self-heal the engine's other locks already had, and a failed acquire no longer leaves the guard pointing at a directory this process did not own.

The daemon validated saved review decisions with a private copy of the contract schema, which made it the one consumer of the closed action table that no conformance test covered. That validator now lives in the shared library as `pg_review_decision_envelope_valid`, the daemon calls it, and the conformance suite proves it accepts every envelope the runtime emits for the frozen corpus and rejects a swapped action, an injected blocking-wait field, a foreign contract digest, and a symlinked file. The same suite now also checks that the skill and relay carry the sized timeouts, so the churn this release removes cannot creep back through a stale hint.

## Fixed

- The default review wait was shorter than the median large review, and the default collection wait was shorter still, forcing repeated collection passes.
- A contended reservation-guard acquire leaked a file descriptor on every timeout.
- The no-`flock` reservation guard could stall on a directory left by a dead process and could release a guard it did not own.
- The daemon's decision validator was a private schema copy outside conformance coverage.
