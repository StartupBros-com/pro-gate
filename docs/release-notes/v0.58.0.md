# v0.58.0

## Highlights

- When a review's attachment fails to reach ChatGPT twice in a row with nothing changed, pro-gate stops and says so instead of trying the same thing again.
- Fixing the cause starts reviews again on their own: a new commit, a different attachment setting, or a newer Oracle build.

## Upgrade

Update the plugin and runtime together to v0.58.0. The review-decision contract gains one stop reason and one fact, so an adapter that pins the contract identity, such as the pi extension, needs its identity updated before it accepts v0.58.0 decisions; until then it stops with the version-update message, as it does for any contract change. Reviews recorded by older runtimes stay readable. Rolling back to v0.57.0 is not seamless: v0.57.0 cannot read reviews started under v0.58.0, so collect or finish those first.

## Details

When Oracle's own session record proves that a review's prompt was never sent, for example because ChatGPT never accepted the attached patch, pro-gate refunds the round. Until now the next decision offered the identical review again, and a caller running pro-gate in a loop kept paying the time for the same failure until its own time budget ran out. Nothing was spent on ChatGPT, but each attempt still took minutes of browser time.

Each refund of that kind now records the conditions the attempt ran under:

- the exact evidence the review was bound to (repository, pull request, commit and patch);
- the input mode;
- the attachment setting, `PRO_GATE_BROWSER_ATTACHMENTS`;
- the installed Oracle build, as `oracle --version` reports it.

It also records how many such refunds in a row that same set of conditions has produced for the pull request. A sent attempt, a finished review, or different conditions in between start the count again. The decision reports the count as `facts.delivery.failed_unchanged`. After two in a row, it returns `stop-without-new-review` with the new reason `delivery-failed-unchanged` instead of a third identical grant.

The stop lifts by itself when anything it recorded changes: a new commit, a different input mode or attachment setting, or a new Oracle build. For a one-off retry with nothing changed, an operator can run one review with `PRO_GATE_FORCE_ROUND=1`; the decision shows that as `facts.delivery.override`. The advisory query and the guarded run build the fact with the same code, so a run that was granted before the second failure is refused before it reaches the browser.

Only a proven no-send counts. A Cloudflare challenge is handled by the account cooldown and is not counted. A failed or disputed proof, a send whose fate is unknown, and runs started without a typed decision record nothing, so they behave as before. The query runs `oracle --version`, with a five-second limit, only when the newest attempt for the pull request is a recorded no-send; ordinary queries do not start Oracle.
