# v0.47.0

## Highlights

- On a Mac, a rare pile-up of runs waiting for the same lock could leave pro-gate spinning at full CPU instead of timing out. It now gives up on schedule.
- Waiting for a busy lock is otherwise unchanged: a lock left by a crashed run is still taken over straight away, and a live holder is still waited out in full.

## Upgrade

Update the plugin and runtime together to v0.47.0. Nothing else to do, and nothing to clear: the change affects only how long a wait may last, not anything written to disk. Linux machines were never affected — the problem only existed on hosts without the `flock` utility, which in practice means macOS.

## Details

Only one review may work on a given pull request at a time, so pro-gate takes a lock before it starts. On Linux it uses the system's own locking utility. macOS does not ship that utility, so there pro-gate falls back to claiming a directory, which is the one operation the filesystem guarantees only one process can win.

That fallback has to cope with locks nobody owns any more — a run killed mid-review, a machine that lost power. So before giving up, a waiting run checks whether the current holder is actually gone, and if it proves the holder is dead it clears the lock and immediately tries again. Retrying at once is the right behaviour: the lock is free and the work should proceed without waiting.

What was missing is that this immediate retry had no limit of its own. The wait budget — the "give up after N seconds" the caller asks for — was only consulted on the other path, the one where the holder is alive and the waiter sleeps. So in the unlucky case where a dead holder's lock is cleared and another process claims the same lock in the instant before the waiting run can take it, over and over, the run retried in a tight loop indefinitely: no pause, no deadline, and one CPU core fully occupied for as long as it lasted.

The retry path now carries its own limit, sized from the same wait budget the caller passed. Every way around the loop now either counts against that limit or waits against the deadline, so the loop cannot run forever regardless of which way the race goes. Nothing else moves: a dead holder's lock is still reclaimed and taken, a live holder is still waited out for the caller's full budget before the wait is refused, and the lock's on-disk record — which other parts of pro-gate read to report what is in flight — is byte-for-byte what it was.

Deliberately, the limit is a count of retries rather than a second deadline. A lock abandoned by a run that died at exactly the wrong moment only becomes recoverable after a short settling period, which means the retry that rescues it is often the one that arrives just after the waiting run's own budget has run out. Taking that lock is the entire point of the recovery path, so the clock does not get a vote there; the count is what guarantees the loop ends.

The same defect shape had already been fixed once, in the sibling lock that guards reservation bookkeeping. Every lock that shares this fallback now behaves the same way: the one that reserves a pull request for review, the one that collects a finished review, the one that recovers an interrupted run, and the one that records a review's outcome.

## Fixed

- On hosts without `flock`, `pg_lock`'s reclaim-success path skipped both the wait bound and the sleep, so sustained reclaim-success with the lock still contended was an unbounded busy spin instead of a timeout. Every caller of that lock is covered: the per-change review lock, the harvest lock, the recover lock and the review-effect lock (#189).
