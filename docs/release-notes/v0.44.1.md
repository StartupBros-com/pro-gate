# v0.44.1

## Highlights

- On machines without `flock`, a run that has just taken a lock is no longer at risk of having it reclaimed by another run in the instant before it finishes recording itself.

## Upgrade

Update the plugin and runtime together to v0.44.1. Nothing else to do. Machines with `flock` are unaffected, and so is anyone who never ran v0.44.0.

## Details

v0.44.0 taught the shared reclaimer to read the account-slot and per-change locks, which record their owner as a file inside the lock directory. It treated that file as proof that someone had claimed the lock — but the file is created a moment before the owner's identity is written into it, so for a brief window a run that legitimately holds the lock looks like one that holds it anonymously.

Reclaiming needs a separate rule for that case, and the reclaimer already had one: a lock with no owner recorded is left alone until it has sat that way longer than any live run ever would. v0.44.0 skipped that rule whenever the owner file existed, even while empty. The result was that a run could have its own lock taken away in the gap between claiming it and signing it, letting a second run into the same lock.

The empty record no longer counts as a claim, so the waiting rule applies to it as it always did. Nothing else changes: a lock whose owner is recorded and alive is still held, a recycled process id is still not its original owner, and a lock abandoned with an empty record is still cleaned up once enough time has passed to prove nobody is coming back for it.

The same window is also the lasting state when recording the owner fails outright — a full disk, for instance — so this closes that case too.

## Fixed

- A run could reclaim a lock another run had just taken, in the window before that run finished recording itself (#155).
