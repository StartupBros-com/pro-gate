## Highlights

- Waiting for a review no longer means dozens of manual "are we there yet" status checks — the gate now blocks efficiently until your verdict is ready, then wakes you up.
- A review that goes quiet is now reported as "can't tell what's happening" instead of silently treated as a failure, so a slow-but-healthy run is never mistaken for a dead one.
- The automated review daemon recovers itself the same efficient way, instead of falling back to a fixed sleep-and-check loop.

## Upgrade

Nothing to migrate. In-flight reviews keep running; reattach to one with the run marker from its status file. The new blocking wait is used automatically the next time you run a review.

## Details

Earlier releases required whoever launched a review to poll its status file by hand, roughly every minute, for as long as the review ran (often 10-47+ minutes). This release adds a single blocking wait: launch the review, then wait on it once — no more hand-rolled poll loops, and no tokens spent while genuinely waiting. When the run finishes, the wait returns with the verdict and, if a follow-up step is needed (like collecting a review that outlasted its slot), the exact next command to run.

The wait distinguishes three outcomes: the review reached a verdict, the wait timed out on a still-healthy run (safe to simply wait again), or the run's own status stopped advancing long enough that it can no longer be trusted (an escalation, not a routine retry). That third case now surfaces on its own instead of being confused with either a finished review or a lost session.
