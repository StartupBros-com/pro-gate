# v0.60.0

## Highlights

- A review that never started, because ChatGPT opened no conversation after Send, no longer uses up one of the pull request's review rounds.
- Two of those in a row under the same conditions now stop with a clear reason, instead of quietly spending the day's rounds.

## Upgrade

Update the plugin and runtime together to v0.60.0. Nothing else to do; the review-decision contract is unchanged, so pinned callers keep working.

Downgrading is not seamless: v0.59.x cannot read the record v0.60.0 writes for these attempts, and a pull request that has one stops with `delivery-state-unavailable` until you upgrade again. Stay on v0.60.0, or finish that pull request's reviews first.

## Details

When pro-gate clicks Send and ChatGPT never opens a conversation (the page stays off any conversation, the message box is empty, and a final scan finds nothing), pro-gate has released that attempt since v0.56.0 instead of holding it for six hours. It still counted the attempt as one of the pull request's review rounds, because it cannot prove the message never reached ChatGPT. With the round limit enforced, two or three of these could use up a pull request's rounds for the day after a single real review. On 27 and 28 September, eight pull requests in four repositories reached the round limit with at least one of these attempts counted, and each needed a person to step in.

Such an attempt now counts as a failed delivery, like a send pro-gate can prove never left the browser, and it no longer counts as a round. The existing stop for repeated failed deliveries is what limits it: two failed deliveries in a row with the same code, input mode, attachment setting and Oracle build stop with `delivery-failed-unchanged`. A new commit, a changed setting, a new Oracle build, or the operator's one-run `PRO_GATE_FORCE_ROUND=1` allows another try. "Same code" covers both ends of the comparison: a new base commit that the pull request is compared against also starts the count again, as it already did for sends that provably never left the browser.

When pro-gate cannot tell which Oracle build or which code the attempt used, nothing would stop a repeat, so that attempt keeps its round, as before. The reverse also holds: if a later query cannot read the Oracle build or the pull request's evidence, a pull request whose last attempt was one of these stops with `delivery-state-unavailable` until it can, and `PRO_GATE_FORCE_ROUND=1` does not bypass that stop. Before, such an attempt never caused this stop.

One trade-off: before, two of these on the same commit still left one round for a third try. Now that third try needs a new commit or setting, or the operator's one-run override.
