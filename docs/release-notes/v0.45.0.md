# v0.45.0

## Highlights

- A finished review is no longer discarded when the model retypes its own correlation id in lower case. That mismatch used to read as someone else's review.
- Reviews that stalled forever on "still collecting" for that reason now complete on the first attempt instead of retrying until the run expires.
- A review that genuinely belongs to a different run is still refused, and is now caught in one more case that previously slipped through.

## Upgrade

Update the plugin and runtime together to v0.45.0. Nothing to do. Runs already stuck for this reason recover on their next `--harvest`; no state needs clearing.

## Details

Every review pro-gate submits carries a private correlation id, and the model is asked to repeat it on its final verdict line. That echo is what proves the answer on screen belongs to this run rather than a leftover conversation. The id contains repository text, so it is not all lower case — and when a model helpfully normalised it, pro-gate compared the two spellings literally and concluded the answer belonged to somebody else.

The consequences were expensive, because both halves of the system reached that conclusion independently:

- The browser side declared the conversation cross-bound: it blacklisted the conversation, discarded the note recording where the review lived, and left the finished review unreachable. The run reported a lost review it had already paid for.
- The engine side refused to bind the capture at all. The run kept its reservation, set the capture aside as unbindable, and re-read the same unchanged text on every retry until the reservation aged out.

Both now compare the id the way the surrounding code already reads it — ignoring letter case, and nothing else. Two different runs cannot collide under that rule: an id ends with the launch time and process id of the run that minted it, and one process has exactly one of each. A review naming a different repository, and a sibling attempt of the same round that differs only in its process id, are both still refused; there are tests for each.

The same comparison sits behind the organiser, which renames, archives and closes the conversation once a review lands. It, too, was refusing to act on a run's own conversation. It now acts, and still refuses to touch a conversation whose answer is genuinely another run's.

Two smaller things came out of the same pass and are worth naming:

- An echo written in all capitals used not to be recognised as an id at all. That made a **foreign** all-capitals answer invisible to the cross-conversation check, and salvage would return it as this run's review. The engine's own binding check would then reject it, so no wrong review was ever published — but the browser side should never have offered it. It no longer does.
- The engine's text matching now pins the C locale. Case folding in shell tools follows the host's language settings, and under a Turkish locale `I` does not fold to `i` — which would have quietly reproduced this same bug on those hosts, for any repository whose name contains an I.

## Fixed

- A review whose verdict echoed this run's correlation id in a different letter case was treated as another run's answer: the conversation was blacklisted and its finished review lost (browser side), and the capture never bound and retried until the reservation expired (engine side).
- `--close` left a conversation tab open when the rendered id differed only in letter case.
- The organiser refused to rename, archive or close a conversation for the same reason.
- A foreign correlation id written in all capitals was not recognised as foreign, so salvage returned another run's completed answer as a match.
