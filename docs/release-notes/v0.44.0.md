# v0.44.0

## Highlights

- Reviews that supply results for different tasks are refused before publication or replay, preventing another task's findings or verdict from reaching your fixer.
- Reviews can still quote old verdicts or mention other tasks; clean answers and recovery copies keep their original contents.
- Each review attempt keeps its own session name, including after the review service shortens and normalizes it.

## Upgrade

Update the plugin and runtime together to v0.44.0. Nothing else to do — the next review picks it up automatically.

## Details

Each review prompt asks the model to sign its `VERDICT:` line with the run's own marker. Browser-matched captures require that signature by default; the existing direct-output and explicitly selected legacy exceptions remain unchanged. It checked the end of the answer, which is the wrong place to look when one ChatGPT conversation has received two different runs' prompts and the model has answered both: the page then holds two complete blocks, each signed by a different run. When ours happened to be last, the whole page passed the check and was published. The caller reads the first `VERDICT:` line it finds, so it acted on the other run's verdict and sent a fixer at a path from another repository — and the round was spent without this repository's own result ever being counted.

Collection validates the complete response for this run before publishing it:

- Authoritative verdicts for different runs make the entire answer unusable, in either order. One verdict line claiming two run markers is refused too. The collector does not trim the answer to salvage one task's block.
- A marker in ordinary prose or a quoted, fenced, or indented verdict example is reference text. The browser collector preserves quote and code context when reading the page, and excludes older conversation history before this run's prompt.
- Ownership validation leaves clean captures untouched; the existing removal of the owned run marker remains a separate collection step. Completed or pending recovery artifacts keep their exact bytes. Mixed artifacts from an older version are refused without rewriting or deleting them.
- Rejection keeps diagnostic capture evidence and does not release reservations, charges, or change ownership. Age, an absent spinner or verdict, and repeated refusal are not release proofs; existing authoritative lifecycle proofs remain unchanged.
- A shared mixed conversation cannot be renamed, archived, or closed by either run. The organizer and finalizer retain their independent ownership checks.

The route in is narrowed as well. The Oracle session was named after the pull request, so every round and retry of one PR competed for the same name and was disambiguated with a numeric suffix — a name a later invocation could mint or attach to just as easily. The name now carries the run's own launch time and process id, so no two runs can ask for the same one. It is also short enough to survive unchanged: Oracle shortens a session name to five ten-character words, which quietly reduced longer names back to one shared name.

## Fixed

- A completed review could be published carrying another run's review block, including its verdict line and findings (#164).
- Mixed review blocks could pass ownership checks when the owned verdict happened to be last, or be partially salvaged when it came first (#164).
- A review that quoted a `VERDICT:` line inside one of its own findings had that finding silently trimmed away before publication — including when the quoted line carried another run's marker, which reviews of this repository quote verbatim (#164).
- A rejected capture could lose diagnostic evidence or become eligible for a fresh review solely because its reservation aged out (#164).
- An older answer sitting above this run's prompt in a reused conversation could end recovery for a review that was still being written (#164).
- An answer whose verdict line claimed another run as well as this one, or claimed only another run, could still be published (#164).
- A case-only change to the expected marker is no longer classified as a different task. It remains unbound under the existing exact-signature rule rather than gaining new publication authority (#164).
