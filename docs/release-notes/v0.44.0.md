# v0.44.0

## Highlights

- On machines without `flock`, a lock left by a killed run is reclaimed only when its owner can be proved gone — a recycled process id no longer looks like the original holder.
- Releasing a lock can no longer remove one a different, live run has since taken at the same path.

## Upgrade

Update the plugin and runtime together to v0.44.0. Nothing else to do — the next review picks it up automatically. Machines with `flock` are unaffected: there the kernel releases a lock when its holder dies.

## Details

Where `flock` is missing, the account-slot and per-change locks are directories, and a run killed while holding one leaves its directory behind. Reclaiming those was written separately from the reservation guard's version, and it was weaker in three ways.

Reclaiming is now the same helper the reservation guard adopted in v0.43.0, so all three lock sites answer "is this owner really gone?" the same way and there is one place to harden.

- **A recycled process id no longer reads as the original owner.** Each lock already recorded a process-identity token beside its owner id, but the reclaim path never read it back: a new, unrelated process that happened to receive the same id made the lock look permanently held. The token is now checked, and a mismatch means the lock is stale.
- **Liveness must be proved, not assumed either way.** If the token cannot be recomputed — a transient read under memory pressure — the owner is treated as live and the lock is left alone.
- **Two runs reclaiming the same abandoned lock can no longer both take it.** Reclaiming is not what grants the lock; creating the directory is, and only one creator wins. The loser waits and tries again.
- **A release only removes a lock this run still owns.** A run whose lock was reclaimed while it believed it held it used to delete the path outright on exit, taking whatever the next run had created there. It now checks the recorded owner is still itself, removes its own records by name, and removes the directory only if nothing else holds it.
- **A lock directory whose owner record is empty is reclaimed** rather than wedging the lock forever. A run killed between creating the directory and recording itself used to leave something nothing could clear.

Housekeeping is narrowed to match: the 24-hour sweep of per-change locks now deletes only files, never the fallback lock directories, which have an owner and are the reclaim path's business.

## Fixed

- A process id reused by an unrelated process made a stale no-flock lock look held indefinitely (#155, #152).
- Two waiters reclaiming one abandoned lock could both proceed into it (#155).
- A run's exit could delete a lock directory belonging to a different, live run (#155).
- A lock directory left with an empty owner record could not be reclaimed by anything (#155).
- The 24-hour housekeeping sweep matched the fallback lock directories as well as lock files (#158).
