# v0.40.0

## Highlights

- Every failed review now records why it failed. Until now every failure wrote the same ledger row, so hundreds of them were indistinguishable after the fact.
- The reason is a short fixed vocabulary, never free text, so it stays greppable and can never carry review content into the ledger.
- Nothing about how a review runs, retries, refunds, or holds its slot has changed. This release only records what already happens.

## Upgrade

Update the plugin and runtime together to v0.40.0. Nothing else to do. Rows written before this release keep their old shape; the weekly report labels them as unclassified rather than counting them as one reason.

## Details

The ledger row written at the end of every run gains two fields. `reason` is a closed enum on `failed` rows and an empty string on every other row — present, not absent, matching the convention `marker` and `round_key` set in v0.27. `detail` is the same human-readable string the run already wrote to its `.status` file at the moment it failed.

The engine had been computing the cause and discarding it. Every failure site calls `pg_status failed "<why>"` immediately before it exits, and the true exit-6 site after salvage already builds a `FAIL_DETAIL` string with five distinct values. The one change is at the chokepoint: `pg_status` now remembers the detail it was handed, and the terminal ledger write classifies from flags the run already set.

The enum, derived mechanically from those flags and never from model output:

| reason | meaning |
|---|---|
| `browser-restart` | the review browser restarted mid-run, almost always memory pressure |
| `infra-error` | an exact-owned ChatGPT infrastructure error ended the submitted review; round retained |
| `refunded-unsubmitted` | the prompt provably never reached ChatGPT; round refunded |
| `fate-uncertain` | submission fate could not be proven either way; charged state preserved |
| `salvage-empty` | salvage ran and found no usable review |
| `harvest-failed` | a `--harvest` attempt could not collect |
| `post-dispatch` | failed after a marker and attempt existed, before salvage ran |
| `pre-dispatch` | failed before identity derivation or any browser work |

Two things are deliberately out of reach. Rows whose `outcome` is already specific — `cloudflare`, `lock-timeout`, `oversized`, `round-capped` — get no reason, because the outcome is the reason. And `--recover`'s three "Browser needs attention" exits stay undifferentiated: that path exits bare, never writes a ledger row, and promises exactly one plain state line on stderr, so it has nowhere to put a distinction and the suite asserts it must not grow one.

This is safe to land during a measurement window. The ledger write is the last observable action in `pg_finish`, after the ramp update, which reads only its own state file. Every reader tolerates extra keys: the weekly report uses `row.get()` throughout and the engine suite asserts field presence rather than key-set equality.
