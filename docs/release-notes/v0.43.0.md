# v0.43.0

## Highlights

- On machines without `flock` — stock macOS among them — a reservation guard left behind by a killed process is now reclaimed automatically instead of stalling every later run until someone clears it by hand.
- A guard whose owner is still alive is never reclaimed, including when the check that proves liveness cannot be taken.

## Upgrade

Update the plugin and runtime together to v0.43.0. Nothing else to do — the next review picks it up automatically. Machines that have `flock` are unaffected: there the kernel releases the lock when the holder dies, so there has never been anything to reclaim.

## Details

The reservation guard makes a run's slot accounting and its durable record move together. Where `flock` exists, a killed holder releases it for free. Where it does not, the guard is a directory, and a process killed while holding one leaves it behind: every later acquire waits out its bound and fails. That is a stall rather than a correctness problem — no two runs ever both hold the guard — but it needs a human to notice and clear it.

Reclaiming such a directory is easy to get wrong, and the version that shipped this was rewritten across eight review rounds. What it now does:

- An owner marker records the holder, so a reclaimer can ask whether that process is still alive rather than inferring from the directory's age alone.
- Liveness must be positively disproved. A live process identifier is checked against a start-time token, so a recycled identifier does not read as the original owner. If recomputing that token fails — a transient read failure under load — the owner is treated as live and the directory is left alone. The reclaim path never removes a marker it could not prove abandoned.
- An unmarked directory is reclaimed only after a grace period (`PRO_GATE_DIRLOCK_ORPHAN_GRACE`, five seconds by default). A live contender that has created its directory but not yet written its marker is inside that window, and reclaiming it would hand the guard to two runs at once.
- Reclamation is serialized, so two reclaimers of the same dead owner cannot both proceed.
- A release only ever removes a directory this process still owns, so an orphaned release cannot delete a replacement guard that a live run has since created.
- On shells without `BASHPID`, the fallback publishes the process that actually holds the guard rather than a short-lived inner subshell whose identifier is already gone.

## Fixed

- A reservation guard directory left by a killed process made every later acquire on a no-flock platform wait out `PRO_GATE_RESERVATION_GUARD_WAIT` and fail, until it was removed by hand (#178).
- A reclaimer could remove the guard of a live owner when the start-time token could not be recomputed, handing the guard to a second run while the first was still inside (#178).
- An unmarked guard directory could be reclaimed from under the live contender that had just created it (#178).
- An orphaned release could delete a replacement guard belonging to a different, live run (#178).
