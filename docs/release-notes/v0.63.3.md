## Highlights

- A passing review can be recorded on its pull request again after the default branch has moved since the pull request last synced.
- The merge check now looks for conflicting changes from the exact base the review saw, so commits that landed before recording are checked too.
- A review whose base matches neither the live branch nor the pull request's own base is still refused, as are retargeted or moved pull requests.

## Upgrade

Update the Pro-gate plugin and its matching runtime. Re-run the status recorder for a pull request it refused; this patch does not record past verdicts by itself or change review budgets.

## Details

The optional status recorder (`record-pro-gate-verdict.mjs`) accepted a review only when the review's base equaled the default branch's live tip. The daemon binds each completed review to the pull request's own base snapshot (`base.sha`), which GitHub refreshes only when the pull request syncs. On a repository that merges several times a day the two differ for most open pull requests, so a correct SHIP was refused with "Public review facts or proof do not match the asserted verdict, current head and live default base" and its owner parked (#288).

The recorder now also accepts a review base equal to the pull request's `base.sha`, read from GitHub at recording time, never from the review itself. Base repository and ref must still match exactly, and the head, base tip and default branch are still rechecked before posting. The status records the base the review ran against rather than the tip at recording time, so `--verify-for-merge` checks every commit from that reviewed base to the current tip for overlap with the pull request's files, including commits that landed between the pull request's snapshot and recording. The recorder's output keeps the recording-time tip on a separate `live tip:` line. Callers that inject their own pull request reader without `baseSha` keep the previous live-tip-only rule.
