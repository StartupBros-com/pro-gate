## Highlights

- A review that puts a severity label such as `P1` on its own line, with its finding below, now reports its open counts instead of leaving them unknown.
- Pull requests parked because of those unknown counts can use the completed-review stop again when the review left no open P0.
- Reviews whose label has no finding under it, or has prose, a code block or a different severity there, still report unknown counts and require a fix.

## Upgrade

Update the Pro-gate plugin and its matching runtime. Re-run the parked owner or its stop step; this patch does not rewrite past round history or change review budgets.

## Details

Some reviews write a bare `P1` line as a section label, then a blank line, then the finding (`[P1] path:line — …`). The shared finding parser treated the bare label as an empty blocking label and made both open counts unavailable, so `--review-facts` returned `open_p0: null, open_p1: null` for a review whose P0 section said `none`. The owner's completed-review stop merge then refused with "public review facts have invalid counts", and the round was never written to the governor's history (#291).

A standalone `P0` or `P1` line is now provisional. Blank lines may separate it from an explicit finding of the same severity in bracketed form, and that finding is counted as before. An empty section, a finding of another severity, an unsupported or quoted label, a code fence, prose before the finding, or the end of the review keeps the counts unavailable. Decorated empty labels such as `P1:`, `[P0]` or `**P1**`, `none` declarations, headings, result and input bindings, and review authority are unchanged. Round history recorded before this patch is not backfilled.
